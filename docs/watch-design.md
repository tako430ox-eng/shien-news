## 1. 確認できた問題

- 旧 watch.py は _Walker の文字トークンを連結してハッシュ化する。
  header/nav/footer等は元から省かれるが、aside等の関連情報は本文と一緒に比較される。
  「ページ全体」は厳密にはこの抽出器が残す範囲である。
- 旧差分は短いSHA-1の集合なので、同じ行の出現回数を失う。
  削除数を計算していても報告に出さず、「削除または並べ替え」のままになる。
- 2文字未満の除外と global ignore の ^\d+$ は、単独の金額、年齢、月数等も落とし得る。
- 旧版はリンク先を比較せず、同じラベルの申請先・PDF先の差し替えを見逃し得る。
- PDFのバイト変更とHTMLの削除・並べ替えを同じ説明で報告する。

## 2. 本文と周辺情報

### 大田区にだけ確認済みの範囲を設定

2026-11-25 23:56:28 JSTに現行HTMLを取得して、次を確認した。

| 用途 | セレクタ | 扱い |
|---|---|---|
| ページ見出し | #h1-zone | 本文 |
| 支給対象・金額・期間・申請・JOBOTA・担当課の連絡先 | #main | 本文 |
| 関連情報リスト | #losubnaviinfo01 | 周辺情報。下記の個別照合を行う |
| その他 | 指定範囲以外 | 監視を継続 |

mainタグは本文と側欄の両方を囲むため、mainだけを選んでも今回の誤検知は解消しない。

関連欄の全体は除外しない。設定に記録した次の3種類だけ、**範囲、完全URL、見出し全文**が
すべて一致した単独リンクをnoiseとする。

1. 地域包括支援センター西蒲田の移転のお知らせ
2. 福祉人材育成・交流センター年間予定表（更新日の数字だけ変動を許す）
3. おおた介護のお仕事相談・面接会（開催回数の数字だけ変動を許す）

知らないリンク、同じURLでも見出しに別の文が加わったもの、既知の見出しでもURLが変わったもの、
本文側に移ったリンク、一般の文章は通知する。リンクの一部だけを正規表現で一致させない。
周辺のリンク追加と本文変更が同時に起きても、本文変更を通知する。
抑制した変更の件数・時刻は状態のlast_suppressedに残す。

この3リンク自体のリンク先内容を検査しているわけではない。既知の無関係な告知として、
見出し・URLの変動を限定的に除外する設定であり、対象制度が変わったら設定も再確認する。

### その他のページ

東京都の指定URLはraw取得が403だった。公式の別URLの抽出テキストは閲覧できたが、
実DOMを確認できていないため本文セレクタや周辺欄除外を推測で設定しない。
元の指定URLも変更しない。

本文セレクタ未設定のページは文書全体を監視する。明示した本文範囲の外も、
確認済みの上記リンク以外は基本的に通知する。
旧版で除外されていたheader/nav/footerも監視するので、**通知総数が減る保証はない**。
見逃しを避けるための判断であり、全体の誤検知率の低下を実測したものではない。

ignoreは本文外にだけ全文一致で適用する。現在の設定は「閲覧数・アクセス数・ページ番号」の
ラベルと数値だけのメタデータに限定し、数字全般を除外する規則は削除した。
本文にはignoreを適用しない。

## 3. 比較する単位

scripts/watch_extract.pyが標準ライブラリのHTMLParserで段落、見出し、リスト項目、
表の行などを抽出する。strong/span等の装飾で文章を細切れにせず、全角英数と空白を正規化する。
数字1文字も保持する。

各ブロックのSHA-256には以下を含める。

- 文字列と見出しの文脈
- 本文・周辺・本文外の区分
- リンク先（相対URLを解決し、クエリ・フラグメントは保持）
- 表のセル順、colspan/rowspan等
- 順序付きリストのstart/reversed/type、項目のvalue
- 画像のalt/src、埋め込み先、formの送信先等

電話番号・金額の専用キーワードで重要度を判定しない。
本文のあらゆる文字差分を通知するので、「学生も対象」から「学生は対象外」のような
数値を伴わない条件変更も落とさない。電話リンクのtel:先だけの変更も検知する。

| 観測 | 報告 |
|---|---|
| 追加だけ | 追加件数と今回の該当ブロック |
| 削除だけ | 削除件数、削除候補の旧位置、照合できた現在の見出し |
| 書き換え | 追加と削除をそれぞれ数える。文章同士の意味上の対応は推測しない |
| 個数まで同じで順番だけ変更 | 並べ替えとして通知 |
| 同じ文章が2個から1個になる | 削除1件 |
| 確認済み周辺リンクだけの追加・削除・順序変更 | Issue用レポートを作らず、抑制件数を状態に残す |

集合ではなくCounterで個数を比較する。順序は別に比較し、純粋な並べ替えを削除と混同しない。
本文の並べ替えも通知する。条件の優先順位や説明との対応が変わる場合があるためである。
見出しや世帯と金額の組合せが変われば、単なる並べ替えではなく内容変更になる。

削除された旧文は復元しない。保存した見出しハッシュが今回の見出しと一致するときだけ、
その現在の見出しを報告できる。同一ブロックが重複する場合、削除位置を一意には決められない。
追加と削除が同時にあるケースでは「書き換えを含む追加と削除」とし、混在する移動量は断定しない。

## 4. 状態と引用の保存方針

状態のschema_versionおよび各snapshot.versionは2。

保存するものは、ブロック・見出し・構造・設定のSHA-256、順序、区分、個数、文字数、
noiseの判定、取得時刻、異常の短い理由。本文・見出し・リンクラベルの原文は保存しない。
リンク先もブロックのハッシュに含めるだけで、監視対象のURL以外は状態に列挙しない。
ハッシュは暗号化ではなく、既知の短い文を推測して照合できることには留意する。

レポートには今回取得した追加ブロックだけを最大15件・各120文字まで載せる。
比較用に文字を正規化した抄録であり、逐語引用と同じではない。
Markdown/HTMLとメンションをエスケープする。削除文の架空の復元やAIによる要約は行わない。

回帰テストは架空の小さなHTMLと、PDFの形式判定用の合成バイト列を使う。
実ページ全文をテストフィクスチャ、パッチ、Git履歴には入れない。

## 5. PDFと取得・構造異常

PDFは全文抽出せず、バイト列全体のSHA-256を比較する。
クエリ付きPDF URLもパスで判定する。Content-Typeだけを信用せず、%PDF-の署名と末尾付近の
%%EOFを確認する。PDFを装ったHTML、切断したPDF、矛盾するContent-Typeは異常通知とし、
正常な基準を更新しない。これは最低限の形式検査であり、PDFの完全な構文検証ではない。

PDFの変更は「PDFバイト列の変更」と報告する。本文、画像、メタデータのどれが変わったかは
判定しない。メタデータだけの差でも通知するので、PDFの誤検知削減はこのパッチの範囲外。
本文のPDFリンクの差し替えはHTML側でも検知するが、**同じURLのリンク先PDFの中身**は、
そのPDF自体をpagesに登録して初めて監視できる。現在の47対象にはPDF URLが8件ある。
HTMLからリンクされたPDFをすべて再帰取得する処理は追加していない。

以下はreviewまたはinspection_errorとして通知し、最後の正常なsnapshotを保全する。

- 設定したセレクタの欠落・複数一致・重複範囲・閉じ位置不明
- 空本文、最低文字数未満、必須確認語がない
- 本文が200文字以上あったページで、文字数が前回の35%未満になる
- 本文・周辺欄のタグや祖先構造が変わる
- 未設定ページのmain / role=main / articleの構造が変わる
- title/h1が既知のアクセス拒否・ページなし・メンテナンス等のエラー文に全文一致する
- 文字化け、未対応のContent-Type、HTML/PDFの形式変更
- 設定の変更、対応していない版や壊れたsnapshot

35%は健全性確認を促す保守的な閾値で、制度変更の重要度を決めるものではない。
閾値以上の小さな変化もすべて通常の内容変更として通知する。
空/異常な応答で基準が置き換わり、次回から無変化になることを、判定できる範囲で防ぐ。

通信失敗はunreachableとして別に保持し、回復すれば通信エラーを消す。
取得に成功しても内容検査に失敗すれば内容の異常は残る。変化なしの回は古いレポートを削除する。

## 6. 移行と運用

### 旧状態からの初回

旧HTMLの状態はリンク先・見出しの関係・本文区分を持たないため、新方式と完全には比較できない。
そこで移行の回だけ、今回の取得を**旧方式（本文の行、header/nav/footer を除く）でも計算し、旧状態の digest と比べる**。

- 同じなら、前回の確認から旧方式で見える変化はないので、移行だけを理由に通知せず、新しい正常な基準を作る。
- 違えば、旧方式と同じく「新しく出てきた行」（最大15行）と消えた行の数を示して通知し、新しい基準を作る。
- 旧状態に行のハッシュがない等、旧方式で比べられないときだけ「移行の確認通知」を出す。

（2026-11-25 追記：受け取ったパッチは HTML の全ページで移行の確認通知を出す設計だった。毎週月曜の確認で
約40ページを読み直す負担になるため、旧方式との比較で前回からの変化だけを知らせる形に改めた。）

旧PDFのdigestは同じバイト列ハッシュなので比較を継続できる。
同一なら移行だけを理由に通知しない。変更していればPDF変更として通知する。
異常な応答からは移行しない。

### 構造や設定を確認して受け入れる場合

通常は既存と同じコマンドで動く。

    python scripts/watch.py

構造・設定変更は自動で正常基準にしない。公式ページで新しい範囲と制度情報を確認し、
必要ならconfigを修正してから、対象URLを明示する。

    python scripts/watch.py --accept-baseline 'https://example.go.jp/confirmed-page'

GitHub の画面からは、Actions の「出典ページの変化の見張り」を手動実行（Run workflow）し、
`accept_baseline` 欄に確かめたURLを入れる（複数は空白で区切る）。

複数URLはオプションを繰り返す。設定にないURLは拒否する。
これは全ページの初期化ではなく、指定URLの正常な取得結果だけを受け入れる操作である。
取得失敗、欠落セレクタ、不正PDF、未知版/壊れた状態は、この指定でも正常化しない。
実際の監視対象URLを使い、更新した状態と報告を通常のレビューで確認する。

移行/採用後も「制度変更なし」の自動判定は行わず、制度説明の修正要否は人が判断する。

## 8. 残る限界

- 東京都のraw HTMLを取得できず、過去の差分原因も不明。除外設定の有効性は実証していない。
- 本番の watch.yml での実行、Issue配信、数週間の継続運用は未検証（初回は2026-11-30の予定）。
- header/nav/footer の変化による通知の増え方は、過去の版での比較を試みたが計測できておらず、未実証。
- 無料運用の構成（標準ライブラリ、47 URL、週1回、外部有料APIなし）は維持する。
  GitHubの将来の料金・上限や、本番の所要時間を保証するものではない。
- HTMLParserはブラウザの完全なDOM/CSS/JavaScript処理ではない。JavaScriptが後で生成する本文、
  同じURLで差し替わる画像内の文字、表示状態だけの変化等は検知を保証しない。
- HTTP 200の独自エラー画面を必ず判別できるわけではない。既知のエラー文、構造、本文量、
  設定済みの必須語で防げない場合、通常の内容変更として通知して基準に採用する可能性が残る。
  主本文を確認できた情報源から順に、範囲と必須語を追加する。
- body範囲の外も保守的に監視するため、共通ナビ変更で通知が増える可能性がある。
  実証した削減は確認済みの関連リンクと表記だけの変動であり、誤検知率の数値は算出していない。
- 旧文を保存しないため削除文の全文差分は作れない。件数・位置・見出しの照合が診断の上限。
- watch.yml は Issue を作ってから状態を保存する（2026-11-25 に順序を変更）。Issue を作れなければ
  状態を保存せず、次回も同じ変化を知らせる。Issue を作った後に保存が失敗した場合は、次回に同じ知らせが重複する。
- 報告は Issue 本文の上限（65,536文字）より短く保つ。長いときは後のページの詳細を省くが、ページ名とURLは必ず残す。
